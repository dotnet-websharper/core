This is a minor release of WebSharper 10.1. NuGet version `10.1.7`.

Templates for .NET Core SDK: `dotnet new install WebSharper.Templates@10.1.7`

## Enhancements
* #1587 Added a `useLocalReflection` wsconfig setting (default `false`) that gates reflection-based access, during compilation, to types defined in the project that is being compiled: macros/generators, `[<ReflectedDefinition>]` member bodies, and `RequireFeature` types. This is a **breaking change**: a project that both defines and applies any of these on a type in the same assembly must add `"useLocalReflection": true` to its `wsconfig.json` (or set the `WebSharperUseLocalReflection` MSBuild property) to keep compiling; otherwise the compiler now gives a directed error instead of silently loading the just-emitted assembly with Reflection. Usage from a referenced assembly is unaffected by the gating itself. This is a first step towards allowing WebSharper (F#) translation to run in parallel with the .NET compilation.
* The `Compilation.UseLocalMacros` property is now deprecated and merged into `UseLocalReflection` (same backing value). As a consequence, a macro/generator load failure for a **referenced**-assembly macro/generator (e.g. a broken binding) is now a warning with `Undefined` fallback by default, instead of a compile error, unless `"useLocalReflection": true` is set.
* Added a `verifyRPCSignatures` wsconfig setting (default `false`) that controls whether the compiler verifies remote (RPC) method parameter/return types are JSON-codable. This is a **breaking change**: this check previously always ran; it is now opt-in via `"verifyRPCSignatures": true` (or the `WebSharperVerifyRPCSignatures` MSBuild property).
* Added a `parallelCompilation` wsconfig setting (F# only, default `false`) that overlaps F# IL emission with WebSharper translation for faster builds. Requires `useLocalReflection: false`; ignored with a warning otherwise. Settable also via the `WebSharperParallelCompilation` MSBuild property.
