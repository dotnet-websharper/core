## Features

* #1601 Add .NET 11 as a target framework option and the default for all project templates.
  * Add the .NET 11 `MemoryExtensions.Min` and `Max` span overloads, which are now selected for array extension calls.
  * Support `ReadOnlySpan<T>.ToArray` in collection builder methods.
* #1600 Translate C# 15 collection expression arguments, union declarations and patterns, extension indexers, and labeled `break` and `continue`.
  * Added the `Enumerable.Chunk` proxy using the shared `Seq.chunkBySize` implementation.
* #1599 Support FSharp.Core `partitionWith` for arrays, lists, sets, and parallel arrays in JavaScript, with tests for record spreads, extension operators, and all-fields record constructors.
  * Preserve resolved F# extension operators in generic inline calls.

## Performance

* #580 New WebSharper metadata format and serializer.
  * Metadata is read and written by generated F# code instead of reflection: no encoder derivation at startup, no boxing, and no per-node `obj[]`.
  * Strings, type definitions, methods and constructors are written once and referenced by index, integers are variable-length, and member expressions are length-prefixed blocks.
  * The payload is compressed with Deflate at the Fastest level instead of gzip at its default level.
  * Metadata is split into sections (strings, type tables, main info, inline expressions, other expressions, dependency graph), compressed separately. Compiling a library (or proxy) project without dead code elimination or an output folder reads only what translation needs from references: non-inline code and dependency graphs are not decompressed or decoded. Web worker bundles read the rest when needed. On the core build this reads reference metadata about 4 times faster, and the booster caches less.
  * The compiler logs separate stages for loading referenced assemblies, reading and merging reference metadata, encoding and compressing metadata, and the Cecil assembly write.

* #1560 WebSharper output goes into a `<AssemblyName>.websharper` sidecar file next to the assembly: metadata, generated JavaScript/TypeScript code, source maps and sources. Library assemblies stay exactly as fsc/csc wrote them unless extra.files or web worker bundles are embedded, which avoids the assembly rewrite (about 0.5 s on WebSharper.Tests). Website, bundle, offline and service projects still embed their runtime metadata.
  * MSBuild copies the sidecar to the output folder of the project and packs it with `dotnet pack` (with a warning if it is missing). Sidecars of references are not copied to the output folder or published: compilation reads them next to the referenced assembly (the output of the referenced project, or the NuGet package), and the runtime does not need them.
  * The Paket templates of the WebSharper packages list the sidecars next to the dlls.
  * The booster cache is invalidated by sidecar changes too.
  * extra.files of libraries and web worker bundles are web resources in the sidecar instead of embedded resources with `WebResource` attributes, so no library assembly is rewritten. Websites unpack them as before, and `BaseResource` finds them at runtime through the resource hashes in the runtime metadata (`Resources.IsExternalWebResource`).
  * Website, bundle and offline assemblies no longer get extra assembly references to WebSharper libraries: runtime metadata is merged into them, and `deps.json` lists the libraries for loading.
  * No compilation rewrites an assembly with Mono.Cecil any more. Website, offline and service projects embed runtime metadata when the assembly is written:
    * F#: it is passed to fsc as a `--resource`, which fsc reads just before writing the assembly, so F# type checking and code generation still run in parallel with WebSharper translation. RPC verification loads the assembly, so for these projects it runs after the assembly is written. If translation itself needs the assembly (local macros or generators), it is written once without runtime metadata, then again with it.
    * C#: wscsc emits the assembly from its Roslyn compilation of csc's command line, with embedded sources, source link, Win32 resources and strong name signing, keeping the XML documentation and reference assembly csc wrote. It compiles the code while creating the rest of the output, only writing the assembly waits for the runtime metadata. Source generators run only if the result has other definitions than what csc wrote.
    * C# projects pass csc's command line to WebSharper (`ProvideCommandLineArgs`, kept in `obj/<AssemblyName>.websharper.rsp` for when csc is skipped), and WebSharper translates with all of its options and the right assembly name. `WebSharperCompile` runs after `CoreCompile` instead of inside it (`TargetsTriggeredByCompilation`), to see the command line.
  * The attributes-only assembly of Proxy projects and the placeholder assembly of bundle-only projects are written with System.Reflection.Metadata, signed with the project key.
  * The compiler reads assemblies with System.Reflection.Metadata instead of Mono.Cecil: references, WebSharper resources, runtime metadata, Sitelets.Offline and the metadata of WIG-generated assemblies (`Reflector`). The WIG compiler is moved to the new `WebSharper.Compiler.InterfaceGenerator` assembly (in the WebSharper.Compiler.FSharp package).
  * WIG writes its assembly once and creates its metadata from the written image, so the resource hashes in it also cover extra.files.
  * WIG writes its assembly with System.Reflection.Metadata instead of Mono.Cecil, and no WebSharper package depends on Mono.Cecil any more. The generated assembly has only the generated types: the code of the definitions (the interface generator assembly fsc compiled) is no longer copied into it, so it doesn't reference WebSharper.InterfaceGenerator. Its identity, assembly attributes (title, versions, `AssemblyMetadata`...) and Win32 resources (file properties) still come from the fsc output. Output is deterministic, with the module id from the hash of the contents, and strong name signed with the project's .snk key. WebSharper.JavaScript.dll is 353 KB instead of 828 KB.
  * WIG extra.files and embedded JavaScript and CSS files (`EmbeddedResource`) are web resources in the sidecar instead of embedded resources with `WebResource` attributes, like for libraries. Other embedded resources stay in the assembly.
  * Types of the interface generator assembly itself can't be used in the generated assembly (for example as a macro type): this is an error now, previously it gave a reference to a type that only existed by accident.
  * The output merging of `changeTracking` (module `WebSharper.Compiler.Merging`) is moved to its own `WebSharper.Compiler.Merging` assembly (in the WebSharper.Compiler.FSharp and WebSharper.Compiler.CSharp packages), so `WebSharper.Compiler` and the WebSharper.Compiler.Common package don't depend on DiffPlex.
* WebSharper projects produce reference assemblies again (`ProduceReferenceAssembly` defaults to true, also for netstandard2.0), so a change that only affects a library's implementation does not recompile the projects using it. The WebSharper.FSharp and WebSharper.CSharp packages set this default in a `.props` file: the .NET SDK sets it to false before the `.targets` files of packages are imported.
  * The compiler writes a `<AssemblyName>.websharper.stamp` file, a hash of what compiling a library against this one reads (types, addresses and inline code), only rewritten when that changes.
  * Each compilation lists the reference files it read in `obj/<AssemblyName>.websharper.deps`: stamps of libraries for library projects, full sidecars for website, bundle and dead code eliminated projects or ones with web worker bundles. MSBuild adds them to the compilation inputs.
  * The deps file also lists the implementation assemblies of references whose code ran during the compilation: macros, generators, F# source generators and the assemblies they load. Changes in their implementation show neither in reference assemblies nor in stamps, but change the code generated by the projects using them.
  * Library projects (no project type, no output folder) list these files in `obj/<AssemblyName>.websharper.wsdeps` instead, except the assemblies of F# source generators, whose output the .NET compiler compiles. Every WebSharper compilation writes that file. When one of the files it lists is newer, the new `WebSharperCheckTranslation` target makes WebSharper translate the library again also when fsc/csc is skipped as up to date (`--wstranslateonly`). The assembly and reference assembly are left as they are, F# projects are type checked again but not emitted. So a change in the inline code or a macro of a library re-translates the libraries using it without compiling them. Websites, bundles and other projects writing their own assembly still recompile.
  * F# projects keep the WebSharper command line of the last fsc run in `obj/<AssemblyName>.websharper.rsp`, as C# projects do, for these translations.
  * WebSharper reads references from the implementation assemblies next to `ref`/`refint` reference assemblies, as macros and generators run code from them.
  * An F# type provider project referenced by its reference assembly is passed to the F# compiler by its implementation assembly in the project's output folder, as the compiler loads the design-time assembly from that folder. The F# targets pass `@(ReferencePath)` to WebSharper for this (`--implref:`).
  * For WIG, Proxy and BundleOnly projects, the reference assembly is replaced by the final assembly WebSharper writes.
  * wscsc compiles again when the assembly was written after the last WebSharper compilation finished, also when it has the same module version id.
* #580 Runtime metadata of websites, offline sitelets and services (the default `noexpressions` mode) keeps only what the runtime reads: class addresses with the compiled form of static methods, anonymous record shapes (remoting), and the part of the dependency graph that leads to resources. On the UI test sites it is a fifth of its previous size (218 KB to 43 KB) and decodes about twice as fast at startup. The `full`, `inlines` and `notinlines` modes are unchanged.
* Website prebundles are packaged and written in parallel, and so are the per-class JavaScript, TypeScript and declaration files of libraries. Without source maps, the top-level statements of a file are also rendered in parallel. Creating the 8 prebundles of the `tests/Web` site takes 1.0-1.5 s instead of 3 s, and the log shows packaging, JavaScript conversion and writing times for each prebundle.

## Breaking changes

* #1560 The compiler reads WebSharper information of references only from their sidecar files. Assemblies built by WebSharper are marked with `[assembly: AssemblyMetadata("WebSharper.Sidecar", "1")]`, and a marked reference without its sidecar, or with a sidecar written for another build of it, is an error naming the file. The WebSharper targets add the marker to the generated assembly info, or in a generated source file for projects with `GenerateAssemblyInfo` set to false; `WebSharperSidecarMarker=False` turns it off. A reference with WebSharper 10 metadata embedded and no sidecar is reported as needing a WebSharper 11 build.
  * Packages built with `paket pack` need a line for each library in the `files` section of the template, for example `../MyLib/bin/Release/netstandard2.0/MyLib.websharper ==> lib/netstandard2.0`.
  * Sidecars are only needed for compiling against a library, not at runtime. A copy of a library DLL in the output folder of another project has no sidecar: reference the library project or package to compile against it.

* #580 WebSharper 11 can't read metadata written by WebSharper 10 or earlier: recompile every WebSharper library with WebSharper 11. Reading an old library reports that it needs recompiling.
  * `WebSharper.Core.Metadata.IO` is replaced by `WebSharper.Core.MetadataIO`, and `WebSharper.Core.Binary` is removed.
  * In the default runtime metadata, classes have no instance members, constructors, fields, base classes or custom type information (other than anonymous records), and the dependency graph has no nodes that lead to no resources. Runtime code reading these needs `"runtimeMetadata": "full"` (or `inlines`/`notinlines`).
  * Compiler API: `JavaScriptPackager.entryPointBundles` gives the prebundles to package separately, `packageEntryPoint` returns an array. `Graph.GetResourceTrimmedData` and `Info.DiscardNotRuntimeClassInfo` are new. `FrontEnd.WriteDependencies` takes the files of executed references (`FrontEnd.ExecutedReferences`, from the new `AssemblyResolver.LoadedFiles`), and `WebSharper.Compiler.FSharp.Compile.RunFSharpSourceGeneration` also returns the files it loaded. `FrontEnd.WriteDependencies` also takes the files of F# source generators and whether the project can translate without compiling (`WsConfig.CanTranslateOnly`), `WsConfig.TranslateOnly` is new.

* #1560 Compiler API: `Assembly.Raw` (the Mono.Cecil definition) is replaced by `Assembly.Image` (System.Reflection.Metadata) and `TryGetResource`. `Reflector.TransformAssembly` and `FrontEnd.ModifyWIGAssembly` take a `PEMetadata.PEAssembly`, and `Reflector.TransformWSAssembly` (for assemblies of the old WebSharper.TypeScript, unused) is removed. `LoaderUtility.Resolver` is removed. WIG's `CompiledAssembly` (now in `WebSharper.Compiler.InterfaceGenerator`) writes metadata and web resources to the sidecar in `Save` and gets `AddWebResources`, `Assembly` and `WebSharperMetadata` are removed. `FrontEnd.ModifyWIGAssembly` takes the web resources to hash. WIG `CompilerOptions.Kind`, `ProjectDir` and `CompilationKind` are removed (WIG only generates libraries). `StubAssembly`'s PE writing (.snk signing, deterministic module id, Win32 resources) is in the new `PEWriter` module. `CommandTools.RunInterfaceGenerator` moved to `WebSharper.Compiler.FSharp.Compile`, `CommandTools.LoadInterfaceGeneratorAssembly` to `WebSharper.InterfaceGenerator.ExtensionAssembly.Load` (in `WebSharper.Compiler.InterfaceGenerator`): `WebSharper.Compiler`, wscsc and the C# analyzer no longer reference `WebSharper.InterfaceGenerator`.
* #1560 Compiler API: `FrontEnd.ModifyAssembly`, `ModifyCecilAssembly`, `AssemblyChangeStamp`, `EraseAssemblyContents`, `AddExtraAssemblyReferences`, `Assembly.Write` and `Assembly.RawBytes` are removed. `FrontEnd.CreateOutput` returns the generated resources, the runtime metadata to embed and the sidecar entries; `HandleExtraFiles` returns the extra.files to store as web resources.

## Fixes

* #1600 C# language fixes:
  * Preserve local functions, ordinary loop jumps, and `finally` semantics when lowering C# labeled control flow.
  * Resolve inherited C# interface members when translating implementations, including enumerator `MoveNext` and `Dispose` methods.
