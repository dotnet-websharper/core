This is a preview release of WebSharper 11.0.

## Features

* #1618 Made the WebSharper compiler packages smaller, and added the ReadyToRun compilers as optional .NET tools.
  * The `WebSharper.FSharp` and `WebSharper.CSharp` packages contained only the portable compiler (about 15 MB and 12 MB instead of 128 MB and 88 MB), instead of ReadyToRun builds for every platform.
  * Added the `WebSharper.FSharp.Booster` (wsfsc and the wsfscservice booster) and `WebSharper.CSharp.Booster` (wscsc) .NET tools with the ReadyToRun compilers for win-x64, win-arm64, linux-x64, linux-arm64, linux-musl-x64, linux-musl-arm64, osx-x64, and osx-arm64 (other platforms used the portable compiler). Installing one downloaded only the build for the current platform. When a tool manifest visible from the project listed one at exactly the version of the referenced WebSharper package, or no manifest listed it but it was installed globally at that version, the build used it instead of the portable compiler, for example after `dotnet tool install WebSharper.FSharp.Booster --version <WebSharper version>`. A manifest listing another version gave warning WSB9101, and a listed tool that was not restored gave WSB9102; both built with the portable compiler. Installing these tools required .NET SDK 10 or newer.
  * Added the `WebSharperCompilerVersion` property, set by the props of both packages, and `WebSharperUseBoosterTool=false` to skip the tool lookup. An explicit `WebSharperToolPath` still took precedence.
  * The booster (wsfscservice) also ran with the portable compiler, so it worked on every platform .NET supported, including Windows and Linux on ARM, where builds had been standalone before.

## Fixes

* Fixed the booster (`wsfscservice`) failing a build without a message when it could not parse the compile options, for example after `wsconfig.json` became invalid JSON between two `dotnet ws build` runs. It sent two exit codes for the request, `-12211` and then `0`, and dropped the error. It now printed the error as `WebSharper error WS9001`, like a standalone compilation, and returned exit code 1.

## Breaking changes

* #1618 Changed how the WebSharper targets ran the compiler:
  * Ran the portable compiler as `$(DOTNET_HOST_PATH) wsfsc.dll` (or `wscsc.dll`), with the dotnet host of the SDK running the build, instead of `wsfsc.cmd`/`wsfsc.sh` with `dotnet` from PATH. A `WebSharperToolPath` ending in `.dll` also ran with the dotnet host.
  * Without a ReadyToRun build, F# compilation used the booster instead of compiling standalone. `WebSharperStandalone=True` still turned the booster off.
  * The packages no longer contained the `tools/net11.0/<rid>` folders. A `WebSharperToolPath` pointing into them had to point to the Booster tool or to `tools/net11.0/wsfsc.dll` instead.
  * The booster client found a running booster by connecting to its named pipe instead of looking for a `wsfscservice` process, and started `wsfscservice.dll` with the dotnet host when there was no runnable `wsfscservice` executable next to it.
