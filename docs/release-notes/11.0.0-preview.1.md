This is a preview release of WebSharper 11.0. NuGet version `11.0.0.688-preview.1`.

Templates for .NET Core SDK: `dotnet new install WebSharper.Templates@11.0.0.688-preview.1`

## Features

* #1601 Add .NET 11 as a target framework option and the default for all project templates.
  * Add the .NET 11 `MemoryExtensions.Min` and `Max` span overloads, which are now selected for array extension calls.
  * Support `ReadOnlySpan<T>.ToArray` in collection builder methods.
* #1600 Translate C# 15 collection expression arguments, union declarations and patterns, extension indexers, and labeled `break` and `continue`.
  * Added the `Enumerable.Chunk` proxy using the shared `Seq.chunkBySize` implementation.
* #1599 Support FSharp.Core `partitionWith` for arrays, lists, sets, and parallel arrays in JavaScript, with tests for record spreads, extension operators, and all-fields record constructors.
  * Preserve resolved F# extension operators in generic inline calls.

## Performance

* #580 New WebSharper metadata format and serializer.
  * Runtime metadata of websites, offline sitelets and services (the default `noexpressions` mode) keeps only what the runtime reads: class addresses with the compiled form of static methods, anonymous record shapes (remoting), and the part of the dependency graph that leads to resources. On the UI test sites it is a fifth of its previous size (218 KB to 43 KB) and decodes about twice as fast at startup. The `full`, `inlines` and `notinlines` modes are unchanged.
* #1614 WebSharper output goes into a `<AssemblyName>.websharper` sidecar file next to the assembly: metadata, generated JavaScript/TypeScript code, source maps and sources. Library assemblies stay exactly as fsc/csc wrote them, which avoids the assembly rewrite (about 0.5 s on WebSharper.Tests). Website, bundle, offline and service projects still embed their runtime metadata.
* #1615 Incremental compilation:
  * WebSharper projects produce reference assemblies again (`ProduceReferenceAssembly` defaults to true, also for netstandard2.0), so a change that only affects a library's implementation does not recompile the projects using it. The WebSharper.FSharp and WebSharper.CSharp packages set this default in a `.props` file: the .NET SDK sets it to false before the `.targets` files of packages are imported.
  * The booster (wsfscservice) keeps what reading each F# source file into WebSharper's representation added to the compilation, for the last 20 compiled projects, and replays it instead of reading the file again. A file is read again when it or a file before it changed (by contents), or the compiler options, a reference assembly (by module version id), the WebSharper view of a reference (its stamp, or its sidecar) or the assembly attributes of the project changed. So a rebuild that only changes WebSharper inputs reads no file, and an edit reads only the edited file and the files after it. A short pass over types, annotations and proxies still runs for every file.
    * `WebSharperReadCache=false` (environment variable of the booster) turns it off, `WebSharperReadCacheProjects` sets how many projects are kept. `WebSharperReadCacheCheck=true` reads replayed files again, translates both and reports a warning if the metadata, errors or warnings differ.
    * Standalone compilations (wsfsc without the booster) don't keep reads.

## Fixes

* #1600 C# language fixes:
  * Preserve local functions, ordinary loop jumps, and `finally` semantics when lowering C# labeled control flow.
  * Resolve inherited C# interface members when translating implementations, including enumerator `MoveNext` and `Dispose` methods.

## Breaking changes

* #1614 The compiler now reads WebSharper information of references only from their sidecar files. Assemblies built by WebSharper are marked with `[assembly: AssemblyMetadata("WebSharper.Sidecar", "1")]`, and a marked reference without its sidecar, or with a sidecar written for another build of it, is an error naming the file. The WebSharper targets add the marker to the generated assembly info, or in a generated source file for projects with `GenerateAssemblyInfo` set to false; `WebSharperSidecarMarker=False` turns it off. A reference with WebSharper 10 metadata embedded and no sidecar is reported as needing a WebSharper 11 build.
  * Packages built with `paket pack` need a line for each library in the `files` section of the template, for example `../MyLib/bin/Release/netstandard2.0/MyLib.websharper ==> lib/netstandard2.0`.
  * Sidecars are only needed for compiling against a library, not at runtime. A copy of a library DLL in the output folder of another project has no sidecar: reference the library project or package to compile against it.
* #580 Metadata API and runtime metadata changes:
  * `WebSharper.Core.Metadata.IO` is replaced by `WebSharper.Core.MetadataIO`, and `WebSharper.Core.Binary` is removed.
  * In the default runtime metadata, classes have no instance members, constructors, fields, base classes or custom type information (other than anonymous records), and the dependency graph has no nodes that lead to no resources. Runtime code reading these needs `"runtimeMetadata": "full"` (or `inlines`/`notinlines`).
* Compiler API changes: 
  * `JavaScriptPackager.entryPointBundles` gives the prebundles to package separately, `packageEntryPoint` returns an array. `Graph.GetResourceTrimmedData` and `Info.DiscardNotRuntimeClassInfo` are new. `FrontEnd.WriteDependencies` takes the files of executed references (`FrontEnd.ExecutedReferences`, from the new `AssemblyResolver.LoadedFiles`), and `WebSharper.Compiler.FSharp.Compile.RunFSharpSourceGeneration` also returns the files it loaded. `FrontEnd.WriteDependencies` also takes the files of F# source generators and whether the project can translate without compiling (`WsConfig.CanTranslateOnly`), `WsConfig.TranslateOnly` is new. `Compilation.StartRecording`, `StopRecording` and `Replay` record and replay what is added to a compilation (`CompilationAction`), `AddGraphNode`, `AddGraphEdge` and `AddRequiredFeature` are new and are used by the F# reader instead of changing `Graph` and creating feature objects itself. `ProjectReader.transformAssemblyWith` takes a `ReadCache.Context`, `MetadataIO.ContentHash` is new.
  * `Assembly.Raw` (the Mono.Cecil definition) is replaced by `Assembly.Image` (System.Reflection.Metadata) and `TryGetResource`. `Reflector.TransformAssembly` and `FrontEnd.ModifyWIGAssembly` take a `PEMetadata.PEAssembly`, and `Reflector.TransformWSAssembly` (for assemblies of the old WebSharper.TypeScript, unused) is removed. `LoaderUtility.Resolver` is removed. WIG's `CompiledAssembly` (now in `WebSharper.Compiler.InterfaceGenerator`) writes metadata and web resources to the sidecar in `Save` and gets `AddWebResources`, `Assembly` and `WebSharperMetadata` are removed. `FrontEnd.ModifyWIGAssembly` takes the web resources to hash. WIG `CompilerOptions.Kind`, `ProjectDir` and `CompilationKind` are removed (WIG only generates libraries). `StubAssembly`'s PE writing (.snk signing, deterministic module id, Win32 resources) is in the new `PEWriter` module. `CommandTools.RunInterfaceGenerator` moved to `WebSharper.Compiler.FSharp.Compile`, `CommandTools.LoadInterfaceGeneratorAssembly` to `WebSharper.InterfaceGenerator.ExtensionAssembly.Load` (in `WebSharper.Compiler.InterfaceGenerator`): `WebSharper.Compiler`, wscsc and the C# analyzer no longer reference `WebSharper.InterfaceGenerator`.
  * Compiler API: `FrontEnd.ModifyAssembly`, `ModifyCecilAssembly`, `AssemblyChangeStamp`, `EraseAssemblyContents`, `AddExtraAssemblyReferences`, `Assembly.Write` and `Assembly.RawBytes` are removed. `FrontEnd.CreateOutput` returns the generated resources, the runtime metadata to embed and the sidecar entries; `HandleExtraFiles` returns the extra.files to store as web resources.
